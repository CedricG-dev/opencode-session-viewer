- stance: Creative Partner; techniques chosen by facilitator: Job to Be Done, SCAMPER Method, Role Playing, One Feature Only
- (technique) started Job to Be Done
- (insight by user) the real job: track cost across multiple sessions, and when sessions run concurrently, see each one's task progress at a glance
- (idea by coach) home view = grid of live session cards (cost ticker + current task), auto-sorted by cost burn rate or 'stuck' (no progress in N minutes)
- (idea by user) need both: an overview of all sessions AND an easy way to focus/zoom into one
- (idea by coach) clicking a card expands it in-place into full detail (graphs + task list); the rest of the grid collapses into a thin sidebar rail, one click to flick back out
- (decision by user) single-page app, no persistent data store for v1 (in-memory/session-lifetime state only)
- (technique) started SCAMPER Method
- (decision by user) primary constraint: minimal install friction for end user, open to any better mechanism than plugin-launches-a-server
- (idea by coach) the plugin IS the server: since it runs inside the opencode host process already, it spins up a tiny built-in HTTP server (stdlib only, zero new deps) on first session and reuses it after; installing the plugin = installing the viewer, nothing separate to deploy
- (idea by coach) recommend SSE (EventSource) for live push (one-way, auto-reconnect, plain HTTP, no deps) + plain HTTP endpoints for UI actions like focus-switch; WebSocket is overkill since browser never needs to push data back
- (decision by user) confirmed: SSE for live push, plain HTTP for actions; no bidirectional control needed (no pause/kill from dashboard)
- (decision by user) discovery via fixed/free port picked by first plugin instance; server releases the port and shuts down once all opencode sessions are closed
- (idea by coach) lockfile in temp dir stores port+PID; new instances check PID alive before joining vs re-claiming a fresh port; last session out deletes lockfile and shuts server down
- (technique) started Role Playing
- (idea by user) budget-conscious user needs: total cost per session, its cost progression over time, and an easy way to spot which session is the expensive one
- (idea by coach) each session card shows a live cost sparkline (not just a number); the most expensive card auto-flags visually (color/badge) so it pops without needing to sort
- (idea by user) trust comes from transparency: show the pricing/rate used per model (e.g. $/1M tokens) so users can verify how the cost was computed, not just trust a black-box number
- (idea by coach) cost number has a hover/tooltip 'receipt': model name + rate per token type + counts per type (in/out/cache) -> the breakdown doubles as the token-type-usage view
- (technique) started One Feature Only
- (decision by user) priority: cost tracking + task progress are must-have for v1; multi-session grid/focus nav is important but ranks below the two must-haves
- (decision by user) grid view is needed from day one, not a v2 upgrade -- v1 scope = grid overview + cost tracking + task progress together, no cut corners
- (decision by user) MoSCoW confirmed for v1: Must=grid overview+cost total/sparkline+task list+click-to-expand focus; Should=cost receipt tooltip (model/rate/token-type)+auto-flag priciest; Could=auto-sort by burn rate+stuck detection; Won't-this-time=bidirectional control+persistence
- (insight by coach) throughline: 'minimal install friction' and 'budget-conscious user's fear' are the same anxiety wearing two hats -- the whole design (zero-dep server, no persistence, transparent cost receipts) optimizes for a tool that is small enough and honest enough to trust immediately
